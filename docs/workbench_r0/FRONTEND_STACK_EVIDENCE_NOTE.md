## 1. Что изменилось после археологии

До R0 развилка формулировалась как «React (Quinta) против Svelte (Tinkuy live UI)». Это была неполная постановка, потому что не был найден третий участник — **WhiteCrow с двумя работающими UI-телами**, включая production Flask-воркбенч с маршрутом графа и инспектором узла.

Правильная постановка после R0: существует **три** живых UI-стека и **два** уже работающих инспектора узла. Задача не в выборе фреймворка, а в том, чтобы не создать четвёртый.

| Стек | Проект | Состояние | Графовая подложка | Инспектор узла |
|---|---|---|---|---|
| React 19 + Vite + TS | Quinta `3963df4` | WORKING, 25 тестов | `@xyflow/react ^12.11.0` + `elkjs ^0.11.1`, 9 типов узлов, кастомные рёбра, 3 оверлея, ELK-раскладка (`SpindleLayout.ts`) | `RightDock.tsx` + `Inspector.tsx`, клиентский, ресайз до 70 % |
| Flask + Jinja2 | WhiteCrow `a140dca` | WORKING, в проде | самописный SVG внутри `FIELD_KERNEL_v6_3_1.html` (225 KB) | `GET /visual/inspector/<node_id>`, серверный, 12 типизированных резолверов с provenance |
| Svelte 5 + Vite | Tinkuy `a72ae99` | WORKING | **нет** | **нет** |

## 2. Оценка трёх вариантов

### Вариант 1 — расширить Svelte-UI Тинкуя

**За:** единый стек внутри Тинкуя; WS/SSE-клиент уже написан (`wsClient.ts`, `stores.svelte.ts`); нет второго деплоя.

**Против (по фактам):**
- Графовая подложка отсутствует полностью. `@xyflow` — React-only; для Svelte пришлось бы брать другую библиотеку и заново писать 9 типов узлов, рёбра, оверлеи и ELK-интеграцию. Это самый дорогой компонент задачи, и он в этом варианте не переиспользуется.
- `RightDock` (164 строки, ресайз, pinned/overlay, вкладки) переписывается.
- `FieldCopilot` (310 строк, механика `LLMActionProposal → onApplyProposal`) переписывается.
- Существующий Svelte-UI — 8 компонентов общим объёмом ~15 KB, ориентированных на наблюдение за живым советом. Воркбенч не переиспользует из них почти ничего: пересечение — только транспорт.

**Цена:** переписывание ~1500 строк зрелого UI-кода, из которых графовая часть — самая рискованная.

### Вариант 2 — отдельное React-приложение, переиспользующее Quinta

**За (по фактам):**
- `RightDock.tsx` — чистый layout-компонент без доменной привязки, все параметры через props. Копируется как есть.
- Графовая подложка Quinta покрывает бо́льшую часть потребности: `@xyflow/react` даёт узлы/рёбра/зум/выделение/минимапу, `SpindleCanvas` + девять типов узлов + `SemanticEdge` + три оверлея показывают, что кастомизация уже отработана. **Коррекция v0.2:** `elkjs` числится в зависимостях, но не используется — раскладка рукописная колоночная (`AgentMapView.tsx:12`). Автораскладку пайплайна придётся делать самим либо подключать ELK впервые.
- `FieldCopilot` даёт готовую механику «генерация возвращается применяемым предложением», что и есть требуемые кнопки INSERT ALL / INSERT SELECTION / APPLY DIFF.
- `AgentFoundryView` даёт модель статусов `active/draft/deprecated/needs_review` + сводку совместимости.
- Зависимостей рантайма всего четыре — react, react-dom, @xyflow/react, elkjs. Легковесно.
- Редактор (CodeMirror 6 / Monaco) в React-экосистеме подключается штатно.

**Против:**
- Два фронтенд-стека в одном продукте.
- Два деплоя, два набора линтеров/сборок.
- Риск расхождения дизайна между live-UI и воркбенчем.

**Смягчение:** live-UI и воркбенч решают разные задачи и почти не пересекаются по экранам. Live-UI — наблюдение за идущим советом. Воркбенч — редактирование пайплайна между прогонами. Это два разных режима работы, а не два вида одного экрана.

### Вариант 3 — headless WorkbenchCore + тонкие фронтенды

**За (по фактам):**
- Ядро задачи не является фронтендовым. Реестр промптов, версии, активация, компиляция, статическая валидация, смок-прогон, телеметрия — это Python-сервисы, живущие рядом с рантаймом.
- В WhiteCrow такое ядро **уже частично написано**: `litops/prompt_engine.py` (загрузка реестра + политики, резолв по id, проверка активации, сборка invocation manifest), `scripts/validate_prompt_bodies.py` (статический валидатор), `litops/web/visual_data.py` (read-only проекционный адаптер с дисциплиной «no mutation»).
- Тинкуй уже читает промпты с диска в рантайме (`persona_layer.py:29,196`, `method_packs.py:49`) — ядро может подменять их без передеплоя.
- При наличии ядра выбор фронтенда перестаёт быть архитектурным решением и становится тактическим: любой фронт разговаривает с ядром по HTTP.
- Это единственный вариант, где WhiteCrow как ветка-адаптер с полевыми проекциями (Mosaic/Cross/Radial/Linearized, `FIELD_PROJECTION_ENGINE_SPEC.md`) может быть подключён без переписывания ядра под node-edge-граф.

**Против:**
- Больше проектной работы на первом шаге: надо зафиксировать контракт ядра прежде, чем рисовать первый экран.
- Соблазн бесконечно проектировать ядро вместо доставки среза.

**Смягчение:** контракт ядра ограничить ровно первым вертикальным срезом. Ядро без фронта бесполезно, поэтому оба пишутся в одном срезе.

## 3. Решение

**Вариант 3 с фронтендом по варианту 2: headless `WorkbenchCore` на Python внутри рантайма Тинкуя + отдельное React-приложение воркбенча, переиспользующее компоненты Quinta.**

Обоснование по evidence, а не по вкусу:

1. **Ядро уже наполовину существует и оно на Python.** `prompt_engine.py` + `validate_prompt_bodies.py` + `visual_data.py` — это три четверти требуемых сервисов ядра, написанных на том же языке, что и рантайм Тинкуя. Переписывать их на TS ради «одного стека» — потеря без выигрыша.

2. **Самый дорогой UI-компонент существует только на React.** `@xyflow/react` + `elkjs` + 9 кастомных узлов + ELK-раскладка. В Svelte этого нет ни в Тинкуе, ни где-либо ещё в пространстве проектов. Выбор Svelte означает написать это с нуля.

3. **Требование handoff «не создавать второй RightDock/Canvas/Cockpit» выполняется только в этом варианте.** `RightDock` берётся из Quinta, инспектор-резолверы — по образцу `visual_data.py`, граф — из Quinta. Ничего нового не изобретается.

4. **Полевые проекции WhiteCrow невозможно втиснуть в node-edge-граф.** `FIELD_PROJECTION_ENGINE_SPEC.md` описывает четыре разные проекции одного набора объектов. Если ядро отдаёт типизированные объекты, а не готовый граф, BranchAdapter WhiteCrow сможет отрисовать их по-своему. Если ядро отдаёт граф — не сможет.

5. **Существующий Svelte live-UI не выбрасывается.** Он продолжает делать то, что делает — наблюдение за живым советом через WS. При наличии ядра он получает доступ к тем же данным.

### Что это означает практически

```
WorkbenchCore (Python, в рантайме Тинкуя)
  ├─ AssetRegistry        ← модель prompt_bodies/registry.yaml
  ├─ ActivationService    ← модель activation_policy.yaml
  ├─ PromptResolver       ← адаптация prompt_engine.py
  ├─ StaticValidator      ← адаптация validate_prompt_bodies.py
  ├─ PromptCompiler       ← реализация PROMPT_ORCHESTRATOR_SPEC.md
  ├─ GraphReadModel       ← по образцу visual_data.py, из pipeline.yaml + events.jsonl
  ├─ SmokeHarness         ← поверх существующих examples/ и tests/
  └─ HTTP API             ← /api/workbench/*

Workbench frontend (React 19 + Vite)
  ├─ RightDock            ← COPY из Quinta
  ├─ PipelineGraph        ← @xyflow/react + elkjs, каркас COPY из Quinta
  ├─ NodeInspector        ← ADAPT из Quinta Inspector + WhiteCrow _inspect_*
  ├─ PromptEditor         ← CodeMirror 6, новое
  └─ Copilot              ← ADAPT из FieldCopilot

Tinkuy live UI (Svelte 5) — без изменений
```

## 4. Что этот выбор НЕ решает

- **Дизайнерское расхождение** между Svelte live-UI и React воркбенчем останется. Принимается сознательно.
- **Два деплоя.** Принимается.
- **BranchAdapter для WhiteCrow** в этом решении только становится возможным, но не реализуется. Это отдельная поздняя стадия.

---

## 5. Отвергнутые формулировки

Формулировка «спросить пользователя React или Svelte» **снята**. После археологии выбор определяется фактами: графовая подложка существует только на React, а ядро — только на Python. Пользователю остаётся решение о цене двух стеков, а не о технологии.
