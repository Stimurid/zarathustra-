## ADR-09. Структурный отпечаток вместо счётчика дефектов

Грандфазеринг по количеству (`18 ≤ 18`) заменён сравнением множеств пар `(категория, элемент)`. Категорий шесть, набор закрыт: неизвестная категория не может быть амнистирована по построению. Амнистия только при строгом включении. Waiver требует `reason` и `adr_ref`, привязан к активу, живёт в `drift_waivers.json`.

Счётчик `drift_size` сохранён, но только для отчётности — в решении не участвует.

## ADR-10. Явное намерение правки разводит C1 и C2

Изменение поля контракта физически лежит внутри защищённой области. Введено `intent`:

- `content` — по умолчанию; защищённые области обязаны совпасть с baseline побайтово, иначе сервер отказывает до записи;
- `contract_revision` — единственный путь тронуть контракт; кандидат помечается `contract_revision=True`, попадает под полную силу C1 и требует waiver на каждый новый дефект.

Это усиление: раньше правка контракта была неотличима от правки текста.

## ADR-11. Защита не зависит от фронтенда

Проверка защищённых областей живёт в `WorkbenchService.update_source`, до записи. Подсветка в CodeMirror — аффорданс, не граница. Все отказы уходят в `rejections.jsonl` с актором и деталями. Проверено шестью тестами через сырой HTTP.

## ADR-12. Эквивалентность доказывается payload'ом, не текстом

Единственное принимаемое доказательство — байтовое (или canonical-hash) равенство того, что уходит провайдеру. Живой вывод модели хранится как отдельная семантическая оценка и никогда не служит доказательством. Есть отдельный тест-страховка, фиксирующий, что два разных промпта дают разные payload'ы.

## ADR-13. Три уровня смока

`UNIT_SMOKE` (заглушка) → `INTEGRATION_SMOKE` (capture-провайдер через настоящий `Zarathustra.analyze_situation`) → `LIVE_ACCEPTANCE_SMOKE` (реальный провайдер, пропускается без ключей). Уровни не заменяют друг друга: интеграционный сразу нашёл дефект, невидимый на заглушке (WB-010).

## ADR-14. Идентичность кеша важнее инвалидации

Ключ кеша = `asset_id + variant_id + source_hash + profile_id + activation_revision`. Императивный сброс оставлен вторым рубежом. Прогон берёт неизменяемый снимок активации и живёт под ним до конца.

## ADR-15. У RAG-профиля свои гейты

Общий каркас жизненного цикла, но другая лента: `STATIC_VALIDATE → RETRIEVAL_TEST → DOWNSTREAM_SMOKE` вместо `→ COMPILE → SMOKE`. Состояние `COMPILED` в графе переходов RAG отсутствует физически, а не по соглашению — это проверяется тестом. RAGProfile никогда не проходит через `PromptCompiler`.

## ADR-16. Отсутствующая возможность — не параметр с дефолтом

Девять возможностей помечены `NOT_IMPLEMENTED`: `similarity_threshold`, `reranker`, `diversity_control`, `saturation_criterion`, `retrieval_budget`, `query_rewriting`, `source_weighting`, `embeddings`, кеш результатов. Их нельзя установить, провалидировать или активировать; попытка отклоняется с записью в аудит. В UI они показаны красными пилюлями со статусом, а не полями ввода.

## ADR-17. Градация достоверности сквозная

`MEASURED` / `DERIVED` / `ESTIMATED` / `LLM_EXPLANATION` / `UNKNOWN` проставляется на каждое поле события и каждую метрику сравнения. Оценки (число токенов) никогда не выдаются за измерения и не записываются обратно как конфигурация. `matched_features` всегда `UNKNOWN` — ни один движок не выдаёт признакового вклада.

## ADR-18. Факты извлечения и интерпретация не смешиваются

`explain_candidate` возвращает только то, что движок может подтвердить. `llm_interpretation` по умолчанию `null` и в UI отделён пунктирной рамкой. Формулировки вида «ретривер счёл фрагмент концептуально важным» невозможны: такого сигнала в движке нет.

## ADR-19. Фикстуры подбираются под реальный корпус

Запрос, на который корпус отвечает нулём, делает сравнение бессодержательным. Фикстуры выбраны зондированием корпуса; отдельно оставлена негативная фикстура с нулём хитов, чтобы этот режим тоже был виден.

### WB-009 · Редактор оставался readOnly после клонирования · FIXED

`EditorState.readOnly` фиксировался при создании `EditorView` и не менялся при переключении варианта с BASELINE на кандидата: правки молча не доходили до документа, кнопка «Сохранить» оставалась неактивной. Исправлено через `Compartment` с реконфигурацией. Найдено headless-смоком.

### WB-010 · Capture-клиент не доходил до модельной границы · FIXED

`zarathustra.py:197` маршрутизирует клиента с `provider == "mock"` в детерминированный фолбэк. `CaptureClient` не объявлял `provider`, получал дефолт `"mock"` и никогда не достигал `_llm_situation` — интеграционный смок был бы молча пустым. Исправлено: `provider = "capture"`, с комментарием о причине. **Дефект принципиально невидим на уровне UNIT_SMOKE.**

### WB-011 · `innerText` возвращает CSS-`text-transform` · FIXED

Заголовки `h3` подняты в верхний регистр через CSS; `innerText` возвращает трансформированный текст, из-за чего ассерты вида `includes('Эффективные параметры')` не срабатывали. Текстовые проверки в QA-скрипте приведены к регистронезависимым, структурные — к селекторам.

### WB-012 · `matched_terms` считались по заголовку · FIXED

Совпавшие термы сравнивались с `title + card_id`, а BM25 работает по `_card_search_text`. Поле выходило пустым и бесполезным. Теперь используется собственная searchable-функция движка: для запроса «сцена спор истина» получаем `["истина","спор"]` и `["спор","сцена"]`. Градация — `DERIVED`.

### WB-013 · Корпуса персон пусты · OPEN, данные

Ни у одной из семи персон нет каталога `corpus/`, поэтому `retrieve_initial_context` возвращает 0 чанков в поставке. Не поломка кода. Отражено в профиле полем `source_bindings.corpora_present: false` и предупреждением в UI. Наполнение корпусов — продуктовое решение, не задача Workbench.

### WB-014 · Дефолт `top_k=3` мёртв · OPEN, наблюдение

Все четыре живых вызова передают `top_k=2`; литерал 3 не используется никогда. Перепись показывает обе величины и помечает расхождение. Приведение к одному значению меняет поведение, поэтому оставлено как наблюдение.

### WB-015 · Порядок узлов: retrieval после analyze_situation · OPEN, уточнение

Задание описывало цепочку `retrieve_initial_context → analyze_situation`. В реальном пайплайне порядок обратный: `analyze_situation` производит `situation.topic`, который затем служит запросом для извлечения (`pipeline.py:544`). Граф отражает фактический порядок, а не предполагаемый.
